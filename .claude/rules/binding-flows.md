# Binding flows — auto-bind and the session picker

How a topic actually acquires its binding. The contract these flows serve
(1 topic = 1 binding = 1 session, the two binding shapes, topic lifecycle) is
always-loaded in topic-architecture.md.

**Name-based auto-bind (`_try_auto_bind_topic` in `handlers/commands.py`)**: fired only from `topic_created_handler` (i.e. off the `forum_topic_created` service message, where the name is right there in the event). Order of matches:

1. **Docker agent** — name hits `DOCKER_AGENTS` (`config.get_docker_agent`) → bind `docker:<name>` immediately; the container *is* the "directory" (no tmux window involved). Wins over the tmux-directory branch when names collide (e.g. `~/agents/assistant` exists *and* `assistant` is a docker agent).

2. **Tmux directory** — `_find_matching_dir_for_topic` checks `~/projects/<name>` then `~/agents/<name>` (projects wins on duplicate; underscore-prefixed and dotfile names are skipped — infra/hidden dirs). The bind is **runtime-aware**: `_auto_bind_to_directory` resolves the topic's remembered runtime (`thread_runtime_memory`; falls back to `runtimes.default_runtime()` for never-bound topics, and degrades to the default if the remembered CLI is uninstalled) and uses **that** runtime's `list_sessions` / `create_window(runtime=…)` — a codex topic must rebind as codex, not silently as Claude. On hit the topic binds to the FOLDER and **stops there — no session ever starts without a tap**: `_auto_bind_to_directory` records the directory, lists the runtime's sessions and shows the picker, full stop (state shape reuses what `_handle_session_{select,cancel}` already consume, so no new callback wiring). With nothing to resume the picker still carries the three choices that matter: «➕ New session — <agent>», the «🤖 Agent ▾» switcher, and «📂 Change folder» (`CB_SESSION_BROWSE`) for when the name resolved to the wrong directory. There is **no silent-start path left** — `CCBOT_AUTO_RESUME_AGENTS` was deleted 2026-09-04 (operator: a non-technical user needs the model/folder choice *more*, not less), taking the resume-pinning branch and the `commands.autobind_*` strings with it; a window is created only from `bot._create_and_bind_window` (a picker tap) or `handlers/agent_restart.revive_topic_agent` (🔄 / `/restart` on a topic whose window is gone — same folder, same CLI, same session; see architecture.md). The runtime is written to `thread_runtime_memory` only there, once a window really starts — recording it on the picker path would re-arm the memory of a topic that hasn't chosen yet. Symmetrically, a DELIBERATE end (`/kill`, the panel's kill confirm, closing the topic) calls `session_manager.forget_thread_runtime`, so the next launch asks which agent to run again (the folder memory stays); an involuntary unbind (window died, stale binding, deleted topic) keeps it, so the picker at least opens on the CLI the topic last ran. A `create_window` collision (`ccbot` window already taken → `ccbot-2`) dedups the WINDOW name only — **the topic name is never touched**: it's the user's label (`codex-play` must survive binding to a `demo-api` window), and routing never depends on it (rebinds go through `thread_directory_memory`). The old rename-topic-to-window-name behavior was removed 2026-07-17.

**Scope and known limitation**: the auto-bind only fires when `forum_topic_created` is delivered to ccbot — i.e. the topic was created with ccbot online. Topics created while ccbot was offline, or topics that were *renamed* after creation (the rename produces a separate `forum_topic_edited` service message; the original `forum_topic_created` still carries the old name), fall back to the regular first-message flow: window picker (unbound tmux windows) → directory browser → select directory → session picker (if existing sessions) or create window → bind topic → forward pending message. The Bot API has no `getForumTopic`, so we deliberately don't try to recover the current name out-of-band — anything along those lines (probe-replies, MTProto/telethon, etc.) is rejected as a workaround.

**Resume session flow (picker with agent-switcher)**: On a directory confirm the bot shows the active runtime's resumable sessions as **full-width resume rows** (title + short age — no numbered list in the message text), `➕ Новая сессия — <agent>`, and ONE `🤖 Агент: <name> ▾` switcher row (hidden when only one CLI is installed; initial runtime = `default_runtime()` = `CCBOT_DEFAULT_RUNTIME`, availability-checked). The switcher (`CB_RUNTIME_MENU`) opens a **vertical agent list** (`build_runtime_menu`) — one row per `runtimes.pickable_runtimes()` (gated by `AgentRuntime.is_available`, which falls back to a TTL-cached **login-shell probe** when `shutil.which` misses: the bot's service PATH lacks login-shell-only dirs like `~/.npm-global/bin`, and without the fallback claude's row vanished while its windows launched fine), the active runtime marked `●` with its session count. Every agent row AND `← Назад` route through `CB_RUNTIME_TAB`, which re-enumerates that runtime's sessions (`AgentRuntime.list_sessions` → Claude globs `~/.claude/projects/<cwd>/`, Codex matches `session_meta.cwd` across `~/.codex/sessions/**`, Grok reads its per-cwd group dir) and re-renders the picker in place — the menu holds no state of its own. A resume tap (`CB_SESSION_SELECT`, indices into the cached `SESSIONS_KEY` list; only the newest `PICKER_SESSION_ROWS` are shown) launches on the active runtime. The vertical list replaced a wrapping tab row (2026-07-23 design review) — it stays one row in the picker for ANY number of runtimes. Choosing a Claude session runs `claude --resume <session_id>` (the `--resume` hook reports a new session_id but messages keep writing to the original JSONL; window_state is overridden to track the original id); a Codex session runs `codex resume <id>` (tracking is by cwd, so the rollout is picked up regardless). **A `--resume` from a DIFFERENT cwd duplicates the session id across project dirs** (same id, new JSONL under the new cwd's dir) — the monitor resolves duplicates by newest mtime (`scan_projects` `_offer_session`) and re-tracks at EOF when a tracked session's file path switches (`_process_transcript`); "first found wins" used to silence such topics entirely. A **new runtime** appears in the agent menu automatically by registering in `RUNTIMES` and implementing `list_sessions` — the builder never hardcodes a runtime.

**The pending first message goes through `delivery.forward_pending_text`, never a bare `send_to_window`** — all three forward points (picker resume / ➕ new session in `bot._create_and_bind_window`, the auto-bind and memory-rebind paths in `text_handler`, the window picker's `_handle_win_sel`). A just-launched agent is the likeliest moment for the pane to hold a widget nobody has answered yet, and a blind type+Enter there activates the **preselected** option: Claude Code opens `--resume` on a resume-cost dialog whose preselect is «Resume from summary», so the forward silently compacted away the session the user had just chosen to continue (operator report 2026-08-19; the `ResumePrompt` pattern in `terminal_parser` is what makes it detectable), and a fresh window in an untrusted folder gets the trust prompt. Blocked ⇒ the widget is surfaced (photo + ↑↓⏎) and a background waiter delivers the text the moment the pane frees up (`PENDING_WIDGET_WAIT_SEC`, then a "not delivered" notice) — dropping a message the user already sent would just move the surprise.
